---
title: Build a browser dapp
description: Scaffold a wallet-connected, offline-capable Enbox dapp with live records and the required DWeb service worker.
---

This guide is the default starting point for a browser dapp. It produces the
same application and feature-store structure used by the create-dapp starter
and Notesd: wallet-owned identity, a local IndexedDB replica, shared observable
resources, and a service worker for the offline shell and DWeb resources.

## Create the project

The example uses React and Vite, but the Enbox pieces are framework-neutral.

```bash
bun create vite my-dapp --template react-ts
cd my-dapp
bun install
bun add @enbox/browser @enbox/react
bun add --dev vite-plugin-pwa workbox-precaching workbox-routing
```

`@enbox/browser` supplies the platform-neutral API plus browser wallet and DWeb
helpers. `@enbox/react` subscribes to the same headless stores. The Enbox pieces
need no Node-global or standard-library shims in a Vite browser build.

## Define the application boundary

Give the protocol and schema stable HTTPS identifiers owned by the application.
Changing them later creates a different data model.

```ts title="src/features/notes/protocol.ts"
import { defineProtocol, recordCodecs } from '@enbox/browser';

export type Note = {
  body: string;
  title: string;
};

export const NotesProtocol = defineProtocol({
  protocol  : 'https://notes.example/protocols/notes/v1',
  published : false,
  types     : {
    note: {
      schema             : 'https://notes.example/schemas/note/v1',
      dataFormats        : ['application/json'],
      encryptionRequired : true,
    },
  },
  structure: { note: {} },
} as const, { note: recordCodecs.json<Note>() });
```

Name resources and domain actions once. Input drafts and navigation remain UI
state; protocol paths and record defaults belong to the feature:

```ts title="src/features/notes/store.ts"
import { defineStore } from '@enbox/browser';
import { NotesProtocol } from './protocol.js';

export const NotesStore = defineStore({
  protocols: { notes: NotesProtocol },
  create({ protocols, command }) {
    const notes = protocols.notes.collection('note', { pagination: { limit: 50 } });
    return {
      notes,
      addNote: command((title: string) => notes.create.run({ title: title.trim(), body: '' })),
      loadMore: command(() => notes.loadMore()),
      retry: command(() => notes.retry()),
    };
  },
});
```

Compose features into a static application definition. Its `manifest` is the
source for protocol installation, delegated permissions, sync registration,
and grant refresh:

```ts title="src/app/application.ts"
import { defineApplication } from '@enbox/browser';
import { NotesStore } from '../features/notes/store.js';

export const applicationDefinition = defineApplication({
  stores: { notes: NotesStore },
});
```

Keep one runtime and native connection for the browser application lifetime:

```ts title="src/app/runtime.ts"
import { BrowserConnectHandler, createApplication, createConnectionStore } from '@enbox/browser';
import { applicationDefinition } from './application.js';

let runtime: ReturnType<typeof createApplication> | undefined;

export function getApplication() {
  return runtime ??= createApplication(applicationDefinition, {
    connection: createConnectionStore({
      application: applicationDefinition.manifest,
      connectHandler: BrowserConnectHandler({ appName: 'Notes', appIcon: '/icon.svg' }),
      monitor: { autoRefresh: {} },
    }),
  });
}
```

`applicationDefinition` describes the application; `getApplication()` returns
its live owner. `monitor.autoRefresh` renews delegated grants using the same
manifest. `EnboxProvider` initializes the supplied runtime by default and
leaves its terminal disposal to this browser owner.

Connection UI uses the provider's guarded actions and published flow errors:

```tsx title="src/app/App.tsx"
import { useEnboxConnection } from '@enbox/react';
import { Notes } from '../features/notes/components/Notes.js';

export function App() {
  const connection = useEnboxConnection();
  const busy = connection.isConnecting || connection.isDisconnecting;
  return <main>
    {connection.connectionError && <p role="alert">Could not connect. Try again.</p>}
    {connection.isConnected ? <>
      {connection.walletRepair && <button disabled={busy}
        onClick={() => { void connection.connect().catch(() => {}); }}>Reconnect wallet</button>}
      <Notes disabled={busy || connection.walletRepair !== undefined} />
      <button disabled={busy}
        onClick={() => { void connection.disconnect().catch(() => {}); }}>Sign out</button>
    </> : <button disabled={busy}
      onClick={() => { void connection.connect().catch(() => {}); }}>
      {connection.isConnecting ? 'Connecting…' : 'Connect wallet'}
    </button>}
  </main>;
}
```

`connect()` starts wallet approval directly from the user action. Connection
actions publish their errors and reject actionable failures; this UI handles
the promise and renders the hook's state. Native connection state/actions
remain available through `getApplication().connection`.

When authorization or the SDK facade changes, the runtime retires old feature
instances and `useFeature` resolves their replacements. Components and
controllers share each named resource; they do not recreate query effects.

## Install the DWeb service worker

The service worker is required even if installable-PWA UI is out of scope. It
does two jobs:

1. Workbox precaches the application shell so the local replica remains usable
   without a network.
2. `activatePolyfills()` intercepts DRLs, resolves their DIDs and DWN endpoints,
   and returns records to ordinary `<img>`, `<video>`, and `fetch()` consumers.

Configure Vite to compile one application-owned worker:

```ts title="vite.config.ts"
import react from '@vitejs/plugin-react';
import { defineConfig } from 'vite';
import { VitePWA } from 'vite-plugin-pwa';

export default defineConfig({
  plugins: [
    react(),
    VitePWA({
      strategies     : 'injectManifest',
      srcDir         : 'src',
      filename       : 'sw.ts',
      injectRegister : false,
      manifest       : false,
      injectManifest : {
        maximumFileSizeToCacheInBytes : 8_000_000,
        globPatterns                  : ['**/*.{js,css,html,json,svg,png,ico}'],
      },
      devOptions: {
        enabled : true,
        type    : 'module',
      },
    }),
  ],
});
```

The larger precache limit accounts for the browser SDK in the application
bundle. The worker uses bare package imports; do not add a `process` shim,
dynamic import wrapper, or special IIFE output for Enbox.

```ts title="src/sw.ts"
/// <reference lib="webworker" />

import { activatePolyfills } from '@enbox/browser';
import {
  cleanupOutdatedCaches,
  createHandlerBoundToURL,
  precacheAndRoute,
} from 'workbox-precaching';
import { NavigationRoute, registerRoute } from 'workbox-routing';

declare let self: ServiceWorkerGlobalScope;

precacheAndRoute(self.__WB_MANIFEST);
cleanupOutdatedCaches();
registerRoute(new NavigationRoute(createHandlerBoundToURL('index.html')));

activatePolyfills({
  onCacheCheck: () => ({ ttl: 30_000 }),
});
```

Register and await the worker before initializing Enbox or rendering the app.
This prevents the first screen from issuing DRLs before a worker controls the
page. `prepareBrowser()` waits for the requested registration's active worker
to control this page, then activates page-only DRL links and loading UI without
registering a second worker.

```tsx title="src/main.tsx"
import { prepareBrowser } from '@enbox/browser';
import { EnboxProvider } from '@enbox/react';
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';

import { App } from './app/App.js';
import { getApplication } from './app/runtime.js';

function startApplication(): void {
  createRoot(document.getElementById('root')!).render(
    <StrictMode>
      <EnboxProvider application={getApplication()}>
        <App />
      </EnboxProvider>
    </StrictMode>,
  );
}

function showStartupError(error: unknown): void {
  console.error('Application startup failed:', error);
  document.getElementById('root')!.textContent = 'Application startup failed.';
}

const workerUrl = `${import.meta.env.BASE_URL}${import.meta.env.DEV ? 'dev-sw.js?dev-sw' : 'sw.js'}`;
void prepareBrowser(workerUrl, {
  registrationOptions: { type: 'module', scope: import.meta.env.BASE_URL },
}).then(startApplication).catch(showStartupError);
```

The default 20-second timeout bounds URL registration and the wait for control.
Pass `timeoutMs` to change it, or an `AbortSignal` to cancel the wait when the
caller is disposed. Cancellation does not unregister the worker or undo an
in-progress browser registration. The helper removes its listeners and does
not activate page polyfills after cancellation or failure.

### Reuse a PWA registration

Keep URL registration above for this module-worker recipe. If an existing PWA
registrar owns registration, pass its `ServiceWorkerRegistration` through its
callback instead of adding another registration path:

```ts
function onRegisteredSW(
  _workerUrl: string,
  registration: ServiceWorkerRegistration | undefined,
): void {
  if (registration === undefined) {
    showStartupError(new Error('The application worker could not be registered.'));
    return;
  }
  void prepareBrowser(registration).then(startApplication).catch(showStartupError);
}
```

The existing registrar must match the worker's actual format: `module` for
ES-module output, or `classic` for a classic/IIFE build. For example,
`virtual:pwa-register` uses classic registration in production, so it cannot
register the ES-module worker above. `registrationOptions` applies only to URL
inputs; passing a registration does not register it again or change its type.
Use a registration from this page's `navigator.serviceWorker`, not a wrapper
obtained from another window.

An existing active worker controlling this page is sufficient even when an
update is waiting. Preparation does not call `skipWaiting()`, claim clients,
or reload the page. The worker-side `activatePolyfills()` already calls
`skipWaiting()` and `clients.claim()`; its immediate takeover still applies
when the PWA registrar uses prompt mode. The preparation timeout starts when
the helper is called, after the external registrar has returned a registration.
In React, keep that registrar mounted outside the SDK subtree being gated, and
mount or initialize the subtree only after preparation succeeds.

The page owns the runtime, native connection, and WebSockets. The service worker owns
fetch interception and precaching; browsers may terminate it between events,
so it must not host the long-lived Enbox session.

## Make records drive the UI

The default sync mode is live and WebSocket first. Leave `sync` unset and
subscribe to the feature's collection. Calling this component in multiple
places shares its native observation and mutation progress:

```tsx title="src/features/notes/components/Notes.tsx"
import { useFeature, useStore } from '@enbox/react';
import { useState } from 'react';
import { NotesStore } from '../store.js';

export function Notes({ disabled = false }: { disabled?: boolean }) {
  const feature = useFeature(NotesStore);
  const notes = useStore(feature.notes);
  const creation = useStore(feature.addNote);
  const paging = useStore(feature.loadMore);
  const [title, setTitle] = useState('');
  return <section>
    <form onSubmit={(event) => { event.preventDefault(); void feature.addNote.run(title); }}>
      <input aria-label="Note title" required value={title}
        disabled={disabled || creation.pendingCount > 0} onChange={(event) => setTitle(event.target.value)} />
      <button disabled={disabled || creation.pendingCount > 0}>Add note</button>
    </form>
    {creation.error && <p role="alert">Could not save the note.</p>}
    {notes.status === 'loading' && <p>Loading notes…</p>}
    {notes.status === 'error' && <p role="alert">Could not load notes.
      <button disabled={disabled} onClick={() => { void feature.retry.run(); }}>Try again</button>
    </p>}
    <ul>{notes.records.map(({ record, value }) => <li key={record.id}>{value.title}</li>)}</ul>
    {notes.hasMore && <button disabled={disabled || paging.pendingCount > 0}
      onClick={() => { void feature.loadMore.run(); }}>More notes</button>}
  </section>;
}
```

`ready` means the local result can render. `current` means the relevant remote
replicas have caught up. Keep usable local data on screen while offline and
show freshness separately. Use `records.subscribe()` for an incremental,
append-only history; use `query()` for a one-time search inside domain
operations. Rows are `{ record, value }`: decoded values sit beside their
native record handles.

The runtime owns the native views, while `useStore` retains them after commit
and releases that interest on unmount. Headless controllers resolve the same
feature with `getApplication().store(NotesStore)` and use explicit `retain()`
leases. `ready()` alone temporarily holds the resource until it settles.
Commands publish pending/error state and return their operation result;
application UI still owns draft changes and navigation after an awaited call.

Record handles are live class instances. Pass them through or copy fields such
as `id` and `contextId` explicitly; spreading a handle does not serialize its
accessor properties. A nested collection returns a family whose
`within(parentContextId)` binds its direct parent. Native record operations
supply that context through `parentContextId` on creates and `within` on reads
or views.

## Add multi-party data

Model collaboration in the protocol instead of copying each record into every
user's tenant. Use a `recipient` rule for one record addressed to one DID. Use
a shared context when several related records need roles such as editor and
viewer.

A shared context remains authoritative in its owner's DWN. The owner assigns a
role record whose recipient is another identity, then sends an invitation for
discovery. Acceptance verifies that role and starts an exact-context replica;
both sides then use the same context-bound records API and live views. The
invitation is not the permission, and a local replica is not a second owner.

See [Shared contexts](/docs/packages/api#shared-contexts) for one complete
protocol policy and workflow: role paths, member/viewer actions, owner role
assignment and invitation, recipient acceptance, live access lists, role
changes, revocation, and offline behavior. Use `contexts`, `members`, and
`context.records` from that guide instead of manually threading `from`,
`protocolRole`, or a root `within` through dapp code.

## Hosting requirements

Serve the SPA over HTTPS and route application paths to `index.html`. Apply
these headers at minimum:

```text
/*
  Referrer-Policy: strict-origin-when-cross-origin

/sw.js
  Cache-Control: no-cache, no-store, must-revalidate
```

Do not set `Cross-Origin-Opener-Policy: same-origin`; it disconnects the wallet
popup from `window.opener` and prevents the approval result from returning. If
the app requires cross-origin isolation, use `same-origin-allow-popups` and test
the complete wallet ceremony. A Content Security Policy must allow the app's
HTTPS and WSS DWN endpoints in `connect-src` and the root worker in
`worker-src`.

## End-to-end gate

Build and serve the production output:

```bash
bun run build
bun run preview
```

Before calling the dapp complete, verify all of these in a real browser:

- the first visit reaches an activated worker and
  `navigator.serviceWorker.controller` is non-null;
- wallet approval connects, a reload restores the session, and the UI can ask
  for reapproval;
- creating or changing a record updates an `observe()` view without a timer or
  refresh button;
- a change from another connected tab or device arrives through the live path;
- for a collaborative protocol, two distinct identities prove that an editor
  can mutate, a viewer cannot, role changes take effect, and revocation retires
  retained member handles;
- existing records and the application shell render offline, an offline write
  stays visible, and reconnect eventually makes the view current;
- a real DRL renders and a previously cached DRL remains readable offline;
- sign-out and facade replacement close the old views and subscriptions;
- the deployed `/sw.js`, referrer, popup, CSP, SPA-fallback, and HTTPS settings
  match the requirements above.

For the underlying runtime design, see
[Browser dapp architecture](https://github.com/enboxorg/enbox/blob/main/docs/architecture/browser-dapps.md).
